# 从期望配置到 宿主应用

业务应用负责声明期望状态，宿主应用 负责在明确目标集群后执行受控重建。两者之间是人工复制与确认边界，不是自动跨集群推送。

## client 侧复制

1. 在业务应用打开 `/internal/es/index/desired-state.html`。
2. 找到目标 `indexKey` / 索引行，核对实体、settings、mapping 与字段信息。
3. 点击“复制期望配置”，保留完整 JSON，不手工删改不理解的字段。

## 当前 Adhoc 目标边界

宿主应用 顶栏的全局数据目标选择器通过 `X-Es-Target` 控制 `/cluster/**` 数据面请求，**不控制 Adhoc**。当前 Adhoc 服务仍绑定到 宿主应用 的 host/control-cluster local client；本次 startup-mapping 功能没有改变这条路由。Adhoc target-aware routing 属于更大范围的后续工作，**尚未交付**。

因此，真实业务目标如果不是当前 host/control cluster，只有部署版本同时具备以下三项才能继续：

1. **Adhoc 专属目标选择器**，而不是顶栏全局选择器。
2. **执行预览**明确展示将要写入的目标集群身份、地址、索引和别名。
3. **后端目标路由与确认**，执行请求与作业状态均绑定并校验同一目标。

缺少任一项都必须 **STOP**。不要依赖可见的全局选择器或 `X-Es-Target` 推断 Adhoc 目标；当前仓库没有可替代的任意非 host 目标 Adhoc 工作流，应先协调部署/升级到交付了上述能力的版本。

## 宿主应用 侧执行（仅限已满足目标前置条件）

1. 打开 宿主应用 ES 控制台。
2. 核对 Adhoc 执行预览中的目标集群、地址、索引和别名；不得用顶栏全局选择器代替。
3. 进入 **Adhoc 托管重建**，粘贴期望配置。
4. 先运行配置校验与 dry-run，处理错误和风险提示；不要跳过目标索引、别名与 mapping diff 的检查。
5. 确认执行计划后再执行，观察复制、追平、别名切换和收尾状态。
6. 执行完成后核对新物理索引 mapping、文档数、别名写索引与业务读写。

## 安全前置条件

如果真实目标不是当前 Adhoc 绑定的 host/control cluster，而已部署 宿主应用 缺少 Adhoc 专属目标选择器、执行预览或后端目标路由与确认，立即停止。不要假定“宿主集群”或“控制集群”就是业务目标，也不要靠当前浏览器会话、默认连接或历史记忆推断。

startup reconciler 不处理冲突。日志出现 `CONFLICT` / `action=USE_ADHOC_REBUILD` 时，它只报告 actual、desired 与 path，不会替你创建新索引、迁移数据或切换别名；后续必须走以上 Adhoc 流程。
